## Durable state contract

- Restore the authoritative nonempty state before exposing execution; fail closed on missing original key, invalid ciphertext/schema or revision conflict. Never manufacture a blank installation to repair a failed restore.
- Before every semantic trading transition, persist intent/request identity and await durable acknowledgement. In-memory/local save or a started backup is not acknowledgement. Preserve exact ambiguous intent across restart; no blind resend.
- Bind checkpoint commits to an active instance and expected revision. Reject stale instances/revisions; duplicate checkpoint RPC identities must not create another revision. A lost checkpoint reply is different from a lost broker write; only prove exact stored commit or hold, never dispatch speculatively.
- Encrypt sensitive checkpoint/backup state before crossing storage boundaries. Declare consistent size limits and fail closed when exceeded. Back up changed durable revisions without turning every polling timestamp into an R2 write. R2 backup failure and primary durability are separately visible.
- Keep keys/operations token/bootstrap invitation separate and stable across ordinary deploy/restart. Provide authenticated status/backup/restart/restore operations; do not add a public reset/seed endpoint. Backup restore must preserve high-water revision and require explicit target/action with execution fenced. Stopped broker fixture processes do not prove positions are flat.
- Keep the executor alive independently of a browser through supported scheduling/lifecycle controls. Protect API sessions/Origin at the public origin; private bridge authentication/instance checks must not be bypassed by forged browser headers.

## Integration checkpoints

An encrypted checkpoint bridge can be tested first, but it is not the application. Integrate every generated-app save/restore boundary and serve the actual backend/UI. Report configuration/dry-run, bridge-only probe, app-deployed and nonempty cold-restore as distinct states. For a Python backend, a suitable adapter contract is `restore(instance)` and `commit(expected_revision, mutation_id, encrypted_state)` plus explicit backup/status. Restore can return a prior checkpoint or a proven new empty installation. Every semantic save awaits the commit; ordinary unchanged monitor timestamps need not create revisions. If commit/ack fails, block all dispatch until authoritative state is recovered. Do not silently proceed using an unacknowledged local cache.

## Optional Python/Container infrastructure scaffold

The bundled assets/cloudflare implements an encrypted checkpoint CAS bridge with stale-instance/revision guards and R2 backup; it is reusable infrastructure, not the copy-trading app. scripts/prepare_cloudflare.py creates NEW configuration only (no deployment/overwrite) when the generated app supplies cloud_entrypoint.py, cloud_state.py and pinned requirements.txt. Pass --app, --out, --account-id, --worker, --bucket and --origin with recipient-owned values. The script creates separate STATE_KEY/BRIDGE_TOKEN/OPS_TOKEN/INSTALLATION_INVITATION in an ignored0600file. Preserve it privately; never ship it. Node bridge tests use no cloud services.

The backend must integrate the restore/commit contract; filenames alone do not prove integration. Container env includes STATE_KEY, CLOUD_BRIDGE_URL/TOKEN, APP_INSTANCE_ID, PUBLIC_ORIGIN and APP_PORT8080. GET /__bridge/restore and POST /__bridge/commit require the private bridge token and instance header; commit carries expected_revision, mutation_id, ciphertext, optional keep_alive. This initial scaffold caps encrypted checkpoints at1MiB and fails closed beyond it; enlarge/test limits before bigger journals. keep_alive must include Paused subscriptions still managing owned exposure, not merely browser activity.

Authenticated /__ops/status, /backup, /restart and /restore use the separate OPS_TOKEN, never browser credentials or the bridge token. R2 restore in this scaffold permits ONLY an exact current-revision/hash backup with explicit RESTORE <worker> and broker-exposure acknowledgment, advances the revision and rejects older backup rollback. Catastrophic primary-store loss or older-backup reconciliation is not accepted by this initial scaffold: fence trading and design/review that recovery separately. Never roll an unknown trade journal back silently.

After authorized new-target collision checks, create its separate R2 bucket and run npm ci using the generated pinned deployment manifest/lockfile. Run node tests and wrangler deploy --dry-run against that exact config before wrangler deploy --secrets-file secrets.local.json. Uploading/starting the Container does not prove readiness; verify actual backend/assets/state and cold restore. Retain environment-specific deployment state outside the distributable skill. This probe's synthetic in-container broker has process-lifetime memory: restored app state is not proof that prior synthetic exposure was reconciled after its broker process vanished.

First tested Python runtime pins for the isolated prototype: cryptography46.0.7, cffi2.1.1, pycparser3.12 with a digest-pinned Python3.12image. These are a dated reproducibility example, not a requirement to adopt this stack or an evergreen security recommendation. ## Independent owner storage and observed deployment lessons

The scaffold now generates OWNER_PASSWORD privately alongside the original state/bridge/operations keys and invitation. Native installs explicitly configure INSTALLATION_MODE=native-read-only and the recipient's NATIVE_GATEWAY/NATIVE_PARTNERSHIP_ORIGIN variables in their generated configuration; no broker host or keys are guessed. Keep a synthetic cloud broker design explicit; the scaffold does not silently deploy a fixture.

Integrate GET /__bridge/admin/restore and POST /__bridge/admin/commit using the bridge token and active X-Instance-ID. Owner commit carries expected_revision, mutation_id and encrypted ciphertext, with a 64 KiB limit; validate the echoed identity/revision. Owner checkpoints and owner/ backups are independent of the 1 MiB application checkpoint and checkpoints/ backups. Preserve owner authentication/invitation across application reset and image replacement. Initial OWNER_PASSWORD is bootstrap input, not permission to overwrite a retained rotated password.

The provided /__bridge/reset protocol accepts request_id, expected_revision, encrypted new-state ciphertext, exact RESET <origin> confirmation and acknowledge_broker_exposure=true. The app must persist the reset authorization/job marker, fence mutations, drain business backups and integrate resume/idempotency; the bridge retains owner state while clearing business snapshots and fencing old revisions. Existing in-memory tests are not actual remote application-reset acceptance. Keep reset unavailable until its app-side integration and relevant operational checks are complete.

A successful upload is one checkpoint. Record the Worker version, intended container digest and a known app asset hash. After deployment, compare those values with the active container and an HTTPS response that reaches the application. If Wrangler reports a partial deploy or the API cannot read the uploaded version, inspect the specific failure before retrying. In the recorded replacement, Wrangler 4.152.0 reported upload success followed by a missing version, while 4.165.0 completed deployment. These are observed versions. Verify the supported tool version for the recipient's environment. Allow newly uploaded bindings to propagate before retrying an authenticated operation. [Cloudflare deployment guide](https://developers.cloudflare.com/containers/guides/deploy/).

Record cloud owner access, unknown-intent recovery and settled-checkpoint migration separately. An earlier isolated synthetic deployment demonstrated a nonempty restore and no resend against the same generated broker. A later replacement demonstrated exact settled state transfer and retirement. Each recipient installation needs its own activation and checkpoint verification.

Use an explicit descriptive product User-Agent for server HTTP clients, including the app's checkpoint bridge and any separately hosted synthetic broker. A recipient cloud walkthrough encountered a non-JSON Cloudflare1010 edge refusal with Python's default User-Agent; the explicit client header reached the Worker. Preserve the response classification and unknown-write boundaries rather than treating every403 as retryable. After app restart, reauthenticate each role's browser/test session using its retained authorized pair; server-restored credentials do not restore an expired in-memory session.

## Replace a stuck synthetic test Worker

A deployed Worker can continue serving an old Durable Object container image. Back up the existing test checkpoint and check the actual running image. If a controlled restart still serves the old image, stop repeating the same deployment. Use a fresh isolated Worker and backup bucket when replacement is authorized. [Cloudflare scheduling policies](https://developers.cloudflare.com/containers/configuration/scheduling-policy/).

1. Verify the old synthetic installation has no active execution obligations. Select the exact encrypted business and independent owner backups. Keep the original state key and preserve the source backups. Active or uncertain exposure requires separate reconciliation before migration.
2. Start with a clean destination and protect its initialization. Verify the selected revisions and ciphertext checksum. Transfer both checkpoints before serving the app, preserving identifiers, original mode and retained broker binding. Rotate destination operations and bridge tokens. An import into an empty destination requires an explicit migration path. The scaffold's existing restore endpoint only restores an exact current checkpoint in place.
3. Verify the running app version, signed-in owner access and stored inventory, then make a destination backup. Record broker reachability separately from checkpoint restoration.
4. Retire the original Worker only when the user has authorized retirement and the replacement has passed those checks. Preserve the archived backup and verify the replacement after retirement.
