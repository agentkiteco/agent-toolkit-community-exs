# Broker-backed demo acceptance

Use this milestone after synthetic copying and native read verification. Obtain the client’s explicit approval for the two selected demo accounts and the intended test exposure. Keep all keys in authorized private app storage or process memory. Use a separate application state and deployment target, if deployed. Verify that neither account participates in existing copying and that both broker snapshots match the selected account and start with zero positions and orders.

Verify the exact interpreter used to start the app against its supported version before diagnosing the broker integration. The bundled runtime targets Python 3.12. A local shell version and the service executable can differ. Preserve broker event time and freshness checks. A WebSocket connection or subscription ACK alone proves neither usable market data nor execution readiness.

Set admission through the installation’s ordinary provider controls. With the partner-account requirement enabled, reuse the provider’s retained Partnership key and require the exact investor trade account to appear in the completed account report. Treat a complete empty result as blocked and an unavailable result as pending. When the client authorizes an independent run with this optional requirement off, leave it off in that installation and keep the normal remaining admission and execution checks. Record the filter state with the result.

1. Authenticate both roles in separate sessions. Verify and connect the provider source, publish one test strategy, then connect the investor. Observe the app’s required transaction, quote, account state, configuration and margin baselines for the selected instrument. Use the broker’s confirmed demo flags and read-only snapshots as the starting evidence.
2. Verify Start and Stop with empty accounts. Before opening exposure, verify the supported instrument and live session, both account permissions, permitted size and margin, usable broker quota and a cleanup route. Use one minimum-size source position in 1:1 mode for the initial execution check. Keep the investor effects confined to the app’s journaled execution path. Retain a durable test-order journal and reserve read capacity for checking and closing test positions independently of the diagnostic loop.
3. Match the source and copied effect by exact request, broker result and entity ownership. Record Start, source effect, investor copy, Stop and final broker snapshots independently. Test Stop on the copied position, then close the exact test source position and verify both accounts are flat. If an outcome is unknown, preserve durable evidence and reconcile the existing request before continuing. Capture the first execution hold and its request stage before exercising additional retries.
4. Report the last verified stage and any residual exposure. Record observed effects separately from setup, stream readiness or a refused command. Retain only sanitized results, with no broker keys, private account identifiers or raw payloads in the skill or client package.

Exness can omit the instrument order_types list or return an empty list. The bundled runtime supports the immediate market path in this case after all other checks pass. A nonempty list still restricts the requested type, and the runtime requires an explicit applicable type for pending entries in this increment. [Exness runtime semantics](https://www.exness-api.com/trading/guides/runtime-semantics)

A source transaction can include the position and opening deal while omitting the deal’s order identifier. For a new position within the accepted entry window, use the bundled bounded broker-history check when stream evidence is incomplete. Require an exact opening deal and filled market order linked to the position. Preserve the explicit hold when evidence is missing, contradictory or identifies a pending order. Confirming the source link is a separate milestone from authorizing, submitting and proving an investor fill.

For 1:1, preserve the source lot count without an equity-currency conversion. Check the required margin in the investor currency. Use a direct synchronized quote when available and verify that the contract belongs to the intended account and symbol.

Immediately before dispatch, verify the selected entity and protection across REST and stream observations. Compare identity, state, volume, original creation time and relevant price evidence. Keep transaction-version and connection-generation fences. If final reads outlast a planned quote, use the latest still-valid broker tick, rerun sizing, margin and optional controls, and retain both quote observations. Send only when the original effect and current gates agree.

Omit absent protection levels from new entry requests. Preserve explicit SL/TP levels and the application’s separate protection-edit semantics.
