# Guided delivery and continuity

| Milestone | Client gets | Gate / next input |
| --- | --- | --- |
| M1 local | Provider→strategy→investor→explicit-Start→confirmed synthetic copies in two same-currency modes, persistent state and role guides | M1 outcomes/known gaps; no cloud parameters needed |
| M2 execution/cloud | Same app gains pending/management/recovery, FX/real adapter foundations and durable Cloudflare operation | Recipient resources/authorized local Cloudflare login; nonempty restore/no duplicate dispatch |
| M3 complete target | Admission, Advanced/reviews, reports/fees/CSV, copy link/disconnect and owner console | Feature-map gaps implemented/tested; guides match actual app |
| M4 handoff | The same app, relevant cloud result, actual role/owner guides and final feature-map status | Implemented/partial/missing and checked/not-run remain distinct; no second app rebuild as a normal client milestone |

The kit supports these increments; use release-status.md for demonstrated scope and current limits. Later milestones remain required for a full-parity claim. Do not ship nonworking buttons and count their labels as features. Reports, full pending/recovery, real adapter/policies/cloud remain clearly unavailable until implemented/verified. M1 includes a safe local cleanup Stop; full bounded Stop is M2.

When native copying is requested, choose the [runtime host contract](runtime-integration.md) during M1 schema design, then install/connect its reusable core during native implementation. A verified synthetic cloud delivery completes the scoped synthetic track. It is an intermediate milestone only when the user also requests the broader live target. Continue the missing target actions in that project when the full build is authorized. Independent skill-author evaluations belong outside the normal client build plan.

## Finish the synthetic cloud track

Continue the local project into M2 using generated accounts and an explicit synthetic broker. Verify an ordinary provider-to-investor copy and exact Stop, preserve a nonempty encrypted checkpoint, and confirm the intended app is running in the recipient's isolated account. Follow the [cloud acceptance and migration guidance](cloudflare.md). Give the actual URL, restart and backup instructions, and the English provider, investor, and owner guides. State whether the broker itself retained its prior records. Additional implementation beyond this track follows the user's requested scope.

## Native read-only milestone

Extend the same project after the synthetic foundation. Keep synthetic state sealed in its original installation. Run one [native onboarding sequence](live-read-verification.md#native-onboarding-acceptance) in a separate read-only installation. Find the Gateway and selected accounts from the user's configuration, report independent REST and stream outcomes, verify restart retention and leave Start denied. Check any recipient-owned cloud target as a separate deployment outcome. Ask only for missing private access or the public deployment parameters when the action needs them.

## First client session

1. Inspect the declared workspace, installed tools and existing BUILD_STATE before asking questions. In an empty workspace, use a separate signal2copy project and say where it is. Ask a destination question only when the safe destination is genuinely unclear; do not ask a novice to choose a framework unnecessarily.
2. Explain the immediate value in ordinary language: publish a mock source strategy, connect an investor, explicitly Start and observe an actual synthetic copy. Present the later native/cloud/full-target plan briefly. Missing live keys and cloud setup do not block this session.
3. Begin the first local increment with the bundled M1/fixture/acceptance references. Show a runnable interface checkpoint while continuing implementation, but do not call a static preview or seeded source position a completed copy. Establish one confirmed Proportional path, then finish the other M1 mode/state/Stop requirements. Do not expand into native API, Advanced, full reports or cloud while a mock-only first milestone is the agreed scope.
4. The agent operates the separate fixture control tooling for the demonstration; do not expect the novice to construct broker API requests or provide real accounts. Use normal application role/Connect/Start actions. Supply the documented public demo identities and the path to generated private demo inputs, never operator-control tokens in the app or public guide.
5. Finish the agreed milestone with the local URL, actual startup/restart commands, short role guides, observed copied result and safe Stop instructions. Record any real blocker as a specific missing dependency/behavior, not a broad request for every later credential.

### End and return to a mock session

Use a persistent client project directory; author test directories are disposable and must not become recommended user locations. Before ending a demonstration, guide the client through its safe Stop and actual confirmation. Explain which processes can be stopped independently and what is persistent. The bundled mock broker may keep positions/events only in process memory: restoring the app alone does not restore a stopped broker's records. If those records are gone while an intent/exposure is unresolved, retain the old app state/key and explain the specific recovery limit; do not invent flatness, resend, reset or silently start a replacement project. Offer a clearly separate fresh mock run only as an explicit choice with old evidence preserved. Cloudflare or real keys do not solve this local broker-state loss.

### Questions and later information

Local setup, real broker integration and cloud deployment are distinct tracks. Ask for facts at the action that needs them: local dependencies when tools are unavailable, private Exness access when a specific real integration/read needs it, Cloudflare login and public target parameters when preparing that installation. A synthetic/read-only first cloud release can precede real execution; do not make broker credentials a universal deployment prerequisite. Preserve all supplied answers and the chosen mock-only boundary.

### First milestone handoff

Use a compact client summary: **Working now** (actual behavior and URL), **Checked** (observable result), **Not available yet** (concrete functions), **Next action** (one recommendation and its needed input, if any). Put detailed feature/evidence tables in BUILD_STATE. Tell the client how to resume this same project if its processes stopped. Distinguish generated dummy inputs from real secrets and mock copying from broker integration.

If the client asked only for this first milestone, finish here and recommend the next one. If continuous progress across the larger build was already authorized, continue the next unblocked agreed step without another permission loop. A recommendation does not expand an explicitly limited first-session scope.

## Conversation and progress

- Inspect runtimes/package managers/destination before asking prerequisites. Reuse a suitable installed environment. Dependencies may require normal tool approval; missing cloud information does not block local work.
- Ask destination only if unavailable/ambiguous. In an empty declared workspace with a clear create-app instruction, use a dedicated signal2copy directory and state this assumption. Inspect/continue an existing app instead of replacing it.
- Give stated reversible defaults for optional choices; silence is never a required answer/approval. Ask concise justified questions when their answer becomes necessary. Do not confuse trading account numbers with Cloudflare Account ID.
- On continue, read BUILD_STATE and inspect actual files/processes. Resume the next action, marking stale checks instead of claiming a dead server is running. No repeated setup/reset without cause.
- When the client authorizes continuous progress, report completed outcomes and proceed to the next unblocked milestone without another confirmation. Pause dependent work only for a necessary unanswered fact, an actual tool permission or a material decision outside the agreed scope. If a check consumes disproportionate effort, reconsider its value before adding another test series. A mock-only choice applies to the current iteration: do not repeatedly ask for broker keys while mock-backed work remains possible.
- Preserve request/result evidence and fix concrete failures without weakening ownership/consent. At handoff give startup/test commands, local URLs, synthetic scope, two guide paths, remaining functions and next increment. Include the dependency manifest and reproducible environment setup even if libraries are already installed; a host-specific existing virtualenv path alone is not portable setup.
- Use one BUILD_STATE for decisions/plan/feature statuses, safe commands, evidence, blockers and next step. Tests may produce referenced broker ledgers. This file is not a secret store. Current user instructions override obsolete state within their authorized scope.

## Deployment timing

First Cloudflare deployment belongs in M2: local path and durable/execution foundations first, full reports later. Use new resources/credentials and an isolated synthetic scope; do not touch the reference origin or reset existing installations as a shortcut. Preserve the original encryption key. Verify nonempty accounts/subscription/intent restore and no uncertain-write replay; container-local persistence alone is insufficient.

Real signing/discovery/streams and current Cloudflare APIs must be checked against official documentation at M2. Fixture transport is not real Exness. Cloud/authentication/trades need their own authorization/evidence; missing credentials block only dependent checks. Use cloudflare.md for the concrete cloud delivery/restore gates and broker-adapter.md for verified production boundaries. Do not claim actual deployment or real-broker acceptance until executed.

## Finish the current increment

Before implementing, name its useful observable outcome and a small acceptance scope. Once that outcome is implemented and demonstrated, deliver the updated app/guides and list concrete residual differences separately from unverified scenarios. Do not repeatedly reopen a completed increment or convert every untested permutation into a new requirement. Existing focused evidence may be reused with its actual source/scope; broad reruns need a changed behavior, observed failure or unresolved material concern. Mandatory ownership/consent/durability/unknown boundaries still apply to every enabled trade path.

If the user asks to package or release the skill, finish that artifact from the available evidence. Do not silently expand it into more development of a test application. Name limits honestly and leave further application parity work as a distinct iteration.
