# Bounded real read verification

Use real reads when the next implementation decision depends on signing, routing, permissions or actual response structure. They complement mocked execution/failure scenarios; they do not require a real trade. Announce the transition and precise read scope. Reuse the client's existing encrypted application credentials through authorized private tooling when available. Never request signing secrets in chat, silently import the reference installation's accounts into a recipient build or put secrets/raw account exports in the skill, client ZIP, screenshots or reports.

Keep transport read-only independently of the copying engine: disable native writes and allow only the intended signed GET routes/hosts. Avoid starting, stopping, resetting or deploying the existing application to obtain credentials. If an authorized owner uses an existing encrypted backup to access its own vault, treat it as potentially historical credential evidence, never current execution/position authorization. Keep credentials in memory; delete any necessary private temporary working image. Export only sanitized field/type observations and request outcomes.

Start with provider capability and one selected account's discovery/details, then only the limits/current state/inventory/conditions needed for the decision. Bound requests and avoid repeated discovery after a shared transport failure. History, another account and WebSocket subscriptions are separate additions when needed. A filtered report on the source account can verify report access/schema; it does not establish any investor's eligibility.

## Native onboarding acceptance

1. Continue the same app in a separate installation sealed to native-read-only. Use the client's Gateway from Key Management and the exact selected source and investor accounts. Inspect existing authorized encrypted state first. Obtain any missing pair via a private app form or vault. Treat extracted backup credentials as historical until the real API validates them. Keep credentials and account payloads out of release files, test output and screenshots.
2. Make the broker transport independently read-only. Permit only signed read routes for the chosen accounts and read WebSocket subscriptions. Refuse trading methods even if a host route malfunctions. Check provider capability, source verification, investor sign-in and explicit investor Connect with separate role sessions. Verify the broker response belongs to the exact selected account. Keep provider report access, a matching affiliation row and an empty exact filtered report distinct.
3. Connect read streams with retained access. Observe a matching transaction baseline and mark ticks, floating state and other streams individually. An open socket or control ACK does not count as a synchronized baseline. If the market supplies no tick, report the observation as pending. Do not fabricate freshness.
4. Refuse the read-only Start through the normal app route and verify zero trading writes and no new intent. Restart only the isolated app, keep its original encrypted state and reauthenticate any expired sessions. Confirm retained accounts and Connect state and verify a fresh read. For Cloudflare, check the active image, owner access and read-only deployment independently before calling that target verified.
5. Report the exact verification scope. Confirm each role, verified account binding, relationship result, stream readiness and restart result separately. Do not present a blocked or unattempted check as a failure of the credentials. Demo execution belongs to a later, explicitly scoped milestone with both accounts verified as demo.

Apply the [Access Point discovery rules](https://www.exness-api.com/trading/get-started/access-point-host-discovery). HTTP 429 means throttling. Honor the returned retry delay and keep the account check pending. Avoid retry loops and preserve the resolved per-account Access Point while that runtime is valid. Do not fail over to another account or substitute a connector account for the recipient app's own authentication evidence.

Signed JSON reads can produce finite Decimal objects even when generated fixtures use only integers and strings. Before persisting retained observations or rendering JSON, encode those Decimal values as exact plain decimal strings. Preserve integer and boolean types. Reject unsupported types and nonfinite numbers. Validate live quota metadata in its original domain form before handing it to the quota ledger. The runtime's [checkpoint JSON helper](../assets/runtime/checkpoint_json.py) supplies the narrow serializer.

## Transport lesson from actual execution

The default Python urllib User-Agent received non-JSON HTTP403 responses in the retained environment. An explicit product User-Agent allowed the same signed read paths to succeed. The bundled native transport now sends `Signal2Copy/0.1`; this exact packaged default was checked on live provider/default-link and selected-account discovery/details. An offline check covers the real HTTPS request construction, including preservation of signed headers.

Do not interpret every HTTP403 as invalid keys, foreign-provider status or a definitive scope denial. Preserve the distinction between a numeric documented business response and an unrecognized edge/transport response. Keep signature/body/query rules unchanged, do not forward signed headers on redirects and do not add an automatic retry loop. Fix a demonstrated transport cause, perform one bounded confirmation and record the outcome.

## What the retained real check establishes

Seven read operations/eight signed HTTPS GETs returned200: provider default link; selected source discovery/details, limits, current state, inventory and one instrument condition; filtered client-accounts report. A subsequent three-GET check confirmed the packaged default User-Agent without a test override. These are scoped live HTTP read facts, not browser sign-in, live WebSocket, investor affiliation, order execution or full parity evidence.

A later bounded source-only WebSocket check received both a real transaction initial baseline and a native tick, then closed both subscriptions. Its compatibility fixes are included in the transport: offer the observed server subprotocol `exness-ws-protocol`, and distinguish a correlated subscription control message `{id, code: "200"}` from a business error. Match the locally retained subscription ID; an ACK alone never marks transactions/ticks synchronized. Unknown IDs/status envelopes fail closed. Initial protocol-negotiation and ACK-parser failures are retained. This is sampled live interoperability, not a universal schema guarantee, managed-runtime reconnect test or permission to trade.

Observed on one selected account: top-level account_id/stream_id strings and is_demo boolean; monetary strings in settings/account_state; native position initial_volume/volume/open_price/margin_rate/create_time; nested REST/WebSocket limits; string instrument names; per-instrument contract/volume/margin/session fields. The condition used forex/market/enabled. Values, account identifiers, balances, positions, partner links and keys are excluded from distributable evidence. Report data was empty for the tested source filter, so positive row structure and investor attribution were not live-validated.

The current [instrument reference](https://www.exness-api.com/reference/trading/get-instrument-condition) documents `week_start_time`/`week_end_time` as UTC weekly strings, for example `Mon, 10:00:00`. A bounded evaluator may still lack session support; state that implementation limit instead of claiming UTC is undocumented. Missing boundaries, overlapping rules and HMR semantics still require deliberate handling. A sampled schema is not proof that every optional field or every account has the same shape.

Continue native execution with generated-key injected writes until its actual final session/quota/ownership/RMS and recovery gates are accepted. A confirmed operation status does not identify an owned position by resemblance. Preserve exact request/operation/entity evidence and explicitly held unknown outcomes.
